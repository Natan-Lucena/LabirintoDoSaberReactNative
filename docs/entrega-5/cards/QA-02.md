# QA-02 — E2E com Maestro

| Campo           | Valor                                                                                                                 |
| --------------- | --------------------------------------------------------------------------------------------------------------------- |
| Bloco / onda    | F — Qualidade · E5-11                                                                                                 |
| Classe / modelo | B · Sonnet/Codex (escrita dos fluxos e dos `testID`), esforço médio; C (Haiku) para rodar                             |
| Estimativa      | G · 1–1,5 dia de worker (7 fluxos + `testID` que faltarem)                                                            |
| Dependências    | QA-08 (casos e dados prontos); **autorização do usuário para instalar o Maestro** (fora do projeto) e para o emulador |
| Quem executa    | Worker escreve e roda no emulador; o Victor confere a gravação de cada fluxo                                          |

## 1. Objetivo

Automatizar os fluxos principais do app no emulador, para a regressão das próximas entregas não
depender só da rodada manual. A QA-02 nunca foi feita: o roteiro da Entrega 3
([08-maestro-qa02](../../entrega-3/testes/08-maestro-qa02.md)) já tem as regras, os seletores e os
esqueletos YAML de referência.

## 2. Ambiente

- Maestro CLI instalado **fora do projeto** (nada no `package.json`), com Java; versão anotada
  (`maestro --version`).
- Emulador `Pixel_3a_API_34` com o **Expo Go** (`host.exp.exponent`), Metro em `pnpm start
--clear`, abertura por `openLink: exp://10.0.2.2:8081`.
- Backend real e mocks desligados. Dados por variável (`-e EMAIL=… -e SENHA=… -e
PACIENTE="Paciente Teste Um"`), nunca no YAML.

## 3. Fluxos cobertos

| #   | Fluxo                                                         | Origem              |
| --- | ------------------------------------------------------------- | ------------------- |
| 1   | Login → Início → iniciar sessão → finalizar → salvar evolução | mapa da Entrega 2   |
| 2   | Novo paciente → gerar PDI → salvar                            | mapa da Entrega 2   |
| 3   | Aplicar escala (fictícia) → concluir                          | mapa da Entrega 2   |
| 4   | Gerar relatório → compartilhar (até abrir a folha do Android) | mapa da Entrega 2   |
| 5   | Novo atendimento avulso                                       | mapa da Entrega 2   |
| 6   | Jogar "Forme a palavra" até "Muito bem!"                      | Entrega 5 (ATV-04a) |
| 7   | Criar série semanal de 4 e conferir "Semanal · 1 de 4"        | Entrega 5 (AGE-06)  |

## 4. Plano

1. Pasta `.maestro/` na raiz com `config.yaml`, `subflows/login.yaml` e um arquivo por fluxo
   (`01-sessao-evolucao.yaml` … `07-serie-semanal.yaml`).
2. Seletores por texto ou `accessibilityLabel` (o que o Maestro enxerga). Onde o texto for
   ambíguo (rótulo e `TextInput` com o mesmo nome; letras do jogo), acrescentar `testID` no
   componente da tela, e só nele (o `DsButton`, o `Field` e o `StaticPressable` não repassam
   `testID` hoje: se precisar, repassar a prop é uma mudança de uma linha no componente do
   design system, revisada pelo orquestrador).
3. Cada fluxo limpa o que cria quando possível (exclui o atendimento; a série é cancelada) e usa
   nomes com o sufixo do dia ("Paciente Teste E2E 2611") para não colidir.
4. Documentar em `docs/entrega-5/testes/07-maestro.md`: como instalar, como rodar e os problemas
   conhecidos (LogBox, primeira abertura do Expo Go).

## 5. Critérios de saída

- Os 7 fluxos passam no AVD, **duas execuções seguidas** sem intervenção (AC-QA-02-01).
- Nenhuma credencial ou dado real no `.maestro/`.

## 6. Evidências

Saída do `maestro test` com código 0, relatório `--format=junit` e a gravação de cada fluxo
(`maestro record`), guardados **fora do repositório**; commit e AVD no PR.

## 7. Arquivos

- **Permitidos:** `.maestro/**` (novo), `docs/entrega-5/testes/07-maestro.md` (novo) e, só para
  `testID`, as telas citadas no relato (uma prop por elemento).
- **Proibidos:** `package.json`, lockfile, lógica de telas, testes do Vitest.

## 8. Critérios de aceite

| ID          | Critério                                         | Verificação |
| ----------- | ------------------------------------------------ | ----------- |
| AC-QA-02-01 | Os sete fluxos passam no AVD Android, duas vezes | `E2E`       |

## 9. Riscos e perguntas em aberto

- **Maestro no Windows** (instalação por `.zip`/WSL, Java): se não subir, registrar e parar; não
  instalar nada além do autorizado.
- **IA nos fluxos 2 e 4** (30–45 s): usar `extendedWaitUntil` com tempo de 90 s (G-46).
- **CI:** rodar Maestro no CI fica fora (precisaria de emulador no GitHub Actions); pergunta ao
  usuário se vale uma tarefa futura.

## 10. Fora do escopo

Fluxos de equipe com duas contas, push e iOS (manuais na QA-08 e QA-04).
